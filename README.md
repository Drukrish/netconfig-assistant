# Network Configuration Assistant

A RAG assistant over real IETF RFCs (BGP, OSPF, NAT, DHCP, SNMP, ingress
filtering) that answers network configuration questions with **mandatory,
structurally-verified citations**. A response citing a source that wasn't
actually retrieved is rejected outright — this is the safety mechanism the
whole project exists to demonstrate: a hallucinated network config command
citing a source that doesn't say what the model claims takes down
production, and this project treats that as a correctness requirement, not
an academic metric.

Not "chat with your PDFs" — the corpus is real RFC text, hybrid retrieval
combines vector and full-text search, and the citation guard has caught
**three separate live hallucinations** during development, including a
model inventing eight subsections of RFC 2328 §16 that don't exist.

## Why this exists

Eval design and citation-grounding are two of the most consistently
under-demonstrated skills in AI-engineering hiring. This project is built
specifically to give both a real, working example: not a toy RAG demo, but
a system where a wrong answer is a safety failure, with the guardrails and
eval suite to prove it.

## Architecture

```
corpus/rfcs/*.txt          six RFCs, fetched from rfc-editor.org
   -> chunker.py            splits on the RFC's own numbered sections
   -> ingest.py              fastembed (BAAI/bge-small-en-v1.5, 384-dim)
   -> Postgres + pgvector    226 chunks, HNSW index + generated tsvector

query -> retriever.py        hybrid search: reciprocal rank fusion of
                              vector similarity + full-text rank
      -> generator.py        Claude answers ONLY from retrieved chunks,
                              citing every claim
      -> citation_guard.py    structurally verifies every citation against
                              what was actually retrieved - rejects on
                              mismatch, no exceptions
```

No LLM orchestration framework (LangChain, LlamaIndex, etc.) — the
retrieval, generation, and guardrail layers are hand-rolled on purpose, to
understand and control the actual mechanics rather than trust an
abstraction.

## Stack

Python, FastAPI, SQLAlchemy (async) + asyncpg, Postgres 16 + pgvector,
fastembed (ONNX, no PyTorch — keeps the Docker image lean), raw `httpx`
against the Anthropic API (no SDK), DeepEval for the eval suite, Docker,
Terraform, Kubernetes.

## Real bugs found and fixed (dated, not hypothetical)

A sample — full detail in commit messages:

- **DeepEval silently defaults to OpenAI** whenever a metric's `model`
  param is left unset, confirmed by reading `initialize_model()` directly.
  An unbudgeted second billing surface this project never signed up for.
- **DeepEval's own native Anthropic integration crashes** on Claude's
  adaptive thinking: it hardcodes `message.content[0].text`, assuming
  position 0 is always the text block. It isn't, when a `ThinkingBlock`
  comes first. Fixed by wrapping this project's own `call_claude` (which
  filters by `type == "text"`, not position) instead of DeepEval's
  integration.
- **A pytest-asyncio + async SQLAlchemy engine interaction**: the engine's
  connection pool is created once at import time, but pytest-asyncio
  defaults to a fresh event loop per test — every test after the first
  failed with a `InterfaceError` that looked like a flaky DB, not a loop
  mismatch. Fixed via `asyncio_default_fixture_loop_scope = "session"`.
- **`fastembed` needs a writable HuggingFace cache** to download its model
  on first use — the Docker image's non-root user had none, so the first
  container run failed with a permission error. Fixed by pre-downloading
  the model at build time instead, which also means the deployed container
  needs no network access to HuggingFace at all.
- **A judge-model JSON response silently truncated** mid-object on dense
  RFC sections, at both 1500 and 4000 max_tokens — needed 8000 to reliably
  complete. Same underlying cause as a truncation bug found in an earlier,
  separate project: Claude's adaptive thinking shares the token budget with
  visible output.

## Eval suite

Three layers, all real, none mocked:

1. **Structural citation guard** — 7 pytest cases, no API calls, no DB.
2. **RAG triad** (DeepEval, judged by Claude) — faithfulness, answer
   relevancy, contextual precision, run against a 20-question golden set
   spread proportionally across all six RFCs, generated by the model and
   then **manually reviewed by hand** before being trusted as ground truth.
3. **Live verification scripts** (`scripts/verify_*.py`) — not part of CI,
   a documented record of first-run findings against the real API.

Final baseline: **16/20 passed (80%)**, zero unexplained failures. The 4
that don't pass are all understood: 2 are the citation guard correctly
rejecting real hallucinations (safety mechanism working as designed), 2
are genuine contextual precision weaknesses — the correct chunk was
retrieved but not ranked first — a concrete, measured tuning target
rather than a guess. Two real infra bugs surfaced and fixed along the
way: a judge max_tokens limit that needed to scale with actual retrieved
context size (root cause measured directly, not guessed a third time),
and an httpx timeout too short for the larger response that unlocked.

## Running it locally

```bash
docker compose up -d                    # Postgres 16 + pgvector, port 5433
pip install ".[dev]"
python -m app.services.ingest           # chunks, embeds, loads the corpus
uvicorn app.main:app --reload           # http://localhost:8000
```

`.env` needs `DATABASE_URL` and `ANTHROPIC_API_KEY` (see `app/config.py`
for every setting, including `SPEND_CEILING_USD` — every Claude call is
cost-tracked per-run, and refuses to fire once cumulative recorded spend
hits the ceiling, rather than finding out via a failed request mid-run).

## Deployment

- **Docker** — multi-stage build, verified: builds clean, embeds offline
  (no HuggingFace network needed at runtime), serves `/health` against a
  live Postgres.
- **Kubernetes** — Deployment/Service/ConfigMap/Secret in `k8s/`, verified
  live on a local minikube cluster (not yet deployed to a managed cluster).
- **Terraform** (`terraform/`) — a free-tier-eligible RDS + pgvector
  instance, `init`/`validate`/`plan`/`apply`'d against real AWS.
  Verified live: connected directly and confirmed a real PostgreSQL
  16.13 instance running at the RDS endpoint, not just a green
  Terraform apply log. Security group scoped to a single real IP,
  not open to the world.
- **CI/CD** — three GitHub Actions workflows (`ci`, `docker`, `evals`),
  mirroring the pattern from an earlier project. `ci` and `docker` are
  green. `evals` needs a funded Anthropic API key as a repo secret to run
  (it fails loudly and immediately without one, by design, rather than
  producing a wall of confusing 401s).
